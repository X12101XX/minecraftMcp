# 建造算法与验收参考

本文件只描述 Agent 规划算法；调用字段与限制以连接的 MCP 工具 Schema 为准。不要在 MCP 之外读写世界。

## 1. 选择候选位置

从玩家水平朝向得到前方搜索窗口，不用 pitch 将搜索位置投向空中/地下。建筑至少需要 footprint、总高度、基础深度和外侧维护边距。所有感知和修改区域都必须在用户授权范围内。

按 x/z 柱读取候选支撑高度、空气区间、流体与碰撞障碍。对每个宽 W、长 L 的候选矩形：

1. 排除覆盖未知/未加载区域、危险流体、净空不足、无法支撑的候选。
2. 比较支撑高度极差和预计挖填量；树冠或单个最高非空气点不等于地面。
3. 使用离玩家的距离作为次要指标，优先减少破坏和地形改造。
4. 地形数据在 Y 边界被截断时，扩大获授权的查询范围或判为未知，不推断水底/洞底。

大窗口可用二维前缀和计算矩形障碍数量和挖填量，使用滑动窗口极值计算坡度；普通小窗口直接遍历更易维护。必须先正确再优化。

## 2. 建筑期望与顺序

期望映射键为 dimension + (x,y,z)，值为 block id 和受约束 properties。明确哪些属性要求固定，哪些是允许邻居派生的属性，不能遇到比较失败后临时忽略关键属性。

两层木屋的期望包含基础、地板、墙、二层楼板、屋顶、玻璃、入口、楼梯和全部室内空气。楼梯应连接两层，不被楼板堵住，有足够头部净空。门等多方块结构需要显式放置各组成，不假设直接设置一个方块会模拟玩家物品放置。

顺序：基础/支撑 → 主体与楼板 → 开口和净空 → 楼梯/窗户 → 屋顶细节 → 物理稳定后验证。具体阶段可合并，但依赖阶段必须确认前阶段完成。填充范围互相重叠时明确后写覆盖关系，单个 batch 不提交重复坐标。

## 3. 解码真实查询结果

区域两端包含。sizeX=maxX-minX+1，其他轴同理。X 最快、Z 次之、Y 最慢：

`i=((y-minY)*sizeZ+(z-minZ))*sizeX+(x-minX)`。

索引反解：x=minX+(i mod sizeX)，z=minZ+(floor(i/sizeX) mod sizeZ)，y=minY+floor(i/(sizeX*sizeZ))。

调色板包含完整 ID 与状态。RLE 按顺序展开索引与长度，总长度必须等于体积。检查所有页属于同一查询结果，拒绝缺页、过期或不完整结果。空气也参与解码。不要依赖不透明游标的内部格式或跨结果复用调色板。

## 4. 比较与修复

逐坐标比较预期与实际，O(V) 时间，可流式按块比较以控制内存：

- 期望非空气而实际空气：missing。
- 方块 ID 不同：wrong_block。
- 受约束属性不同：wrong_state。
- 期望空气而实际非空气：unexpected_block。

将差异分组为有界 batch；以刚读取的实际状态作为 expected_state，避免覆盖并发用户修改。流水、重力或邻居更新反复导致相同差异，优先修正结构支撑和计划，不无限设置同一位置。

跨 Tick 采样不具备全区域原子性。对有活动玩家或流体的区域可重读关键分片确认；不能将一次增量查询描述为同一瞬间的完整快照。

## 5. 验收记录

记录世界会话、维度、包围盒、玩家与朝向、任务 ID/终态/计数、读取采样区间、解码覆盖、差异与修复轮次。最终应该能回答：

- 墙壁、两层地板和屋顶是否完整？
- 窗户是否真实为玻璃且开口没有被覆盖？
- 楼梯方向、半部、连接与净空是否符合计划？
- 室内是否有多余方块？
- 所有异步任务是否已终止，失败是否解释清楚？
- 是否只验证内存世界，还是也经过正常保存重启？

最终文字要区分未验证项。不能用图像、统计总数或提交回执替代逐坐标实际验证。
